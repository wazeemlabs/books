## Why it matters

Part III builds a serving engine one mechanism at a time. This chapter
is the starting point: a loop that is completely correct, about fifteen
lines long, and unusable in production for a reason worth measuring
rather than asserting.

It is also not a straw man. This is what everyone writes first, it is
what a tutorial shows you, and — as the end of this chapter argues —
it is what a great deal of production software still does at a
different layer without realizing it.

## The loop

{{ch:what-a-model-does}} described generation as a loop: score every
word, take one, append it, run the whole path again. Written out, that
is:

```python
def naive(model: Model, prompt: list[int], n_new: int) -> Run:
    """Recompute every token's keys and values at every step."""
    seq = list(prompt)
    ...
    for i in range(n_new):
        ...
        logits = forward(model, np.array(seq))
        seq.append(int(logits[-1].argmax()))
        ...
    return Run(tokens=seq[len(prompt) :], ttft_s=ttft, step_s=steps)
```

(`...` is where the timing lives; the file has it in full.)

<!-- defines: autoregressive -->
There is nothing wrong with it. It is the definition of
**autoregressive** generation — each token conditioned on everything
written so far — transcribed into Python, and
{{ch:your-model-on-the-bench}} checked the model underneath it against
PyTorch, so the tokens it produces are the right ones.

Look closely at one line, though:

<!-- abridged: tinyserve/generate.py -->

```python
        logits = forward(model, np.array(seq))
        seq.append(int(logits[-1].argmax()))
```

The model is run over the **entire sequence**, producing scores for
every position. Then `[-1]` takes the last row and throws the rest
away.

## What it computes, and what it needed

Every position's scores get computed. One position's scores get used.

That would be merely inelegant if the discarded work were cheap. It is
not: producing the scores for position 50 means computing that token's
keys, values, attention and feed-forward through every layer. And it
was all computed on the previous step too, from identical inputs, with
identical results.

{{step_growth}}× while the sequence it reprocessed grew
{{seq_growth}}×. Each step costs what it costs because of how much it
redoes.

Since each token costs a little more than the last, the total grows
faster than the number of tokens — and the longer the answer, the
worse the deal. An assistant that writes a paragraph is punished for
it.

## Why the waste is structural

It would be tempting to look for a clever fix inside the loop. There
is not one, and {{ch:what-a-model-does}}'s second fact says why.

A token's keys and values depend on that token and the ones before it,
**never on anything that comes after**. So when the loop recomputes
position 50 on step 51, it computes exactly what it computed on step
50. Bit for bit. It is not approximately the same work; it is the same
work.

The loop redoes it for one reason: **it kept nothing.** Every step
starts from a list of token numbers and rebuilds the entire internal
state from scratch, because nowhere in those fifteen lines is there a
place to put it.

That is the whole diagnosis, and it names the cure. Keep the keys and
values. {{ch:the-kv-cache}} keeps them, in about forty lines, and the
table above becomes a speedup.

> **If you're new here: why not cache everything?**
>
> A reasonable question: why keep only keys and values, rather than the
> whole of each layer's output?
>
> Because keys and values are the only things a *later* token needs
> from an earlier one. Everything else a position computes — its query,
> its attention result, its feed-forward output — is consumed
> immediately to produce that position's own scores, and is never
> looked at again.
>
> {{ch:what-a-model-does}} put it as an asymmetry: keys and values are
> needed forever, queries are needed once. That asymmetry is exactly
> what makes a cache possible, and exactly what fixes its size.

## Where this is soft

**The arithmetic counts are from the shapes, not measured.** They count
every multiply-add in the matrix multiplications and ignore
normalization, softmax and the rest, which are small but not zero. The
discarded *fraction* is robust to that; the absolute figures are
approximate.

**Times are NumPy on a shared machine.** Per
{{ch:your-model-on-the-bench}}, trust the ratios here and not the
milliseconds.

**Attention's quadratic term is small at this model size.** In a larger
model, reprocessing the sequence costs proportionally more than shown
here, because attention grows with the square of length while
everything else grows linearly. The waste is worse for real models, not
better.

## In production

Nobody ships this loop. But the *pattern* — recomputing from scratch
what was computed a moment ago, because nothing was kept — is
everywhere, one layer up:

- **Re-sending the whole conversation to an API on every turn.** The
  provider caches some of it or does not, and either way you are billed
  for reprocessing a prompt whose prefix has not changed. This is the
  same waste with an invoice attached, and
  {{ch:prefix-caching}} is the mechanism that removes it.
- **A long system prompt reprocessed for every request.** A **system
  prompt** is the standing instruction an application puts in front of
  whatever the user typed, and it is the same on every request.
  <!-- defines: system prompt -->
  Identical
  every time, recomputed every time, unless something deliberately
  reuses it.
- **Agent frameworks that rebuild the prompt each turn** and hand the
  server a slightly longer string, with no signal that the first 90% is
  unchanged.

So the question this chapter asks of a loop is worth asking of a
system: **what is being recomputed that did not change?** It is the
first question to ask of any serving stack, and it is usually
answerable in an afternoon.
